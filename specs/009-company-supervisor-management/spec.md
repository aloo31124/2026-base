## Clarifications

### Session 2026-07-29

- Q：公司最小識別資料為何？ → A：使用唯一公司名稱與可選說明，避免引入 Sheet 未要求的統編。
- Q：主管 CRUD 如何綁定既有使用者？ → A：建立主管資料時選擇既有註冊使用者，並授予 `MANAGER` 角色；主管資料保存職稱。
- Q：主管與公司的綁定如何保存？ → A：使用對使用者具唯一限制的公司成員綁定；同一公司可有多人，同一使用者最多一家公司。
- Q：刪除仍有關聯的公司或主管如何處理？ → A：拒絕刪除並要求先取消綁定，避免隱性資料遺失。
- Q：員工一人一公司的規則如何納入本子模組？ → A：綁定表以使用者為唯一鍵，資料模型同時約束主管與員工流程；原先僅有主管 UI，2026-07-30 依 Sheet 第 16 列「預計開發」增量納入員工 UI。

### Session 2026-07-30

- Q：既有「綁定」標籤如何承接主管與員工兩種綁定？ → A：標籤改名為「綁定公司」，標籤內提供主管／員工類型切換，維持單一操作入口。
- Q：哪些使用者可作為員工綁定候選？ → A：限已註冊、啟用且具有 `EMPLOYEE` 角色、尚未綁定公司且尚未建立主管資料的使用者，避免同一人在頁面中出現身分類型歧義。
- Q：員工 API 是否改動既有主管綁定契約？ → A：新增員工專用綁定 API，保留既有主管 `/bindings` 契約，確保既有呼叫端向後相容。
- Q：員工與主管的一人一公司規則如何一致？ → A：兩者共用 `CompanyMembership.user_id` 唯一限制，並由 Service 在寫入前回覆 409 衝突。

## User Scenarios & Testing

### User Story 1 - 管理公司 (Priority: P1)

系統管理員可在「公司」標籤新增、查詢、修改及刪除公司。

**Independent Test**：新增公司後可依名稱查到並修改；取消所有綁定後可刪除。

**Acceptance Scenarios**：

1. **Given** 公司名稱不存在，**When** 管理員新增公司，**Then** 列表顯示新公司。
2. **Given** 公司已存在，**When** 管理員以相同名稱新增或更新，**Then** 系統拒絕重複名稱。
3. **Given** 公司仍有主管綁定，**When** 管理員刪除，**Then** 系統拒絕並提示先取消綁定。

### User Story 2 - 管理主管 (Priority: P1)

系統管理員可在「主管」標籤將已註冊使用者建立為主管、查詢與修改職稱，並在未綁定公司時移除主管身分。

**Independent Test**：選擇既有使用者建立主管後，該使用者取得主管角色；未註冊的使用者識別碼被拒絕。

**Acceptance Scenarios**：

1. **Given** 已註冊且尚非主管的使用者，**When** 管理員建立主管資料，**Then** 主管列表顯示其姓名、帳號與職稱。
2. **Given** 不存在的使用者，**When** 管理員建立主管資料，**Then** 系統拒絕且不建立資料。
3. **Given** 主管未綁定公司，**When** 管理員刪除主管，**Then** 主管資料與附加主管角色一併移除。

### User Story 3 - 管理公司主管綁定 (Priority: P1)

系統管理員可在「綁定公司」標籤將主管綁定至公司、取消綁定，並依公司名稱或主管姓名查詢。

**Independent Test**：一家公司可綁定兩名主管；同一主管嘗試綁定第二家公司時被拒絕；取消後可改綁其他公司。

**Acceptance Scenarios**：

1. **Given** 主管尚未綁定公司，**When** 管理員建立綁定，**Then** 綁定列表顯示公司與主管。
2. **Given** 同一公司已有一名主管，**When** 管理員再綁定另一名主管，**Then** 兩筆綁定皆存在。
3. **Given** 主管已綁定公司，**When** 管理員綁定第二家公司，**Then** 系統拒絕。
4. **Given** 多筆綁定，**When** 管理員輸入公司或主管名稱，**Then** 只顯示相符資料。

### User Story 4 - 管理公司員工綁定 (Priority: P1)

系統管理員可在「綁定公司」標籤切換至員工類型，將符合資格的已註冊員工綁定至公司、取消綁定，並依公司名稱或員工姓名／帳號查詢。

**Independent Test**：將一名員工綁定公司後可依公司與員工名稱查到；同一員工第二家公司被拒絕；取消後可改綁。

**Acceptance Scenarios**：

1. **Given** 已註冊、啟用且尚未綁定公司的員工，**When** 管理員建立綁定，**Then** 員工綁定列表顯示公司、姓名與帳號。
2. **Given** 員工已綁定公司，**When** 管理員嘗試綁定第二家公司，**Then** 系統拒絕且保留原綁定。
3. **Given** 多筆員工綁定，**When** 管理員輸入公司與員工名稱或帳號，**Then** 只顯示同時符合兩項條件的資料。
4. **Given** 員工綁定存在，**When** 管理員取消綁定，**Then** 該筆關聯消失且員工可重新選擇其他公司。

### User Story 5 - 權限與操作頁 (Priority: P1)

只有系統管理員可使用管理 API 與 React 管理頁；頁面沿用 `uiux/` 的側欄、標籤、卡片、表格與表單流程，並將原「綁定」標籤顯示為「綁定公司」。

**Independent Test**：一般使用者呼叫 API 得到 403，直接進入頁面會導向無權限頁；管理員可操作三個標籤及主管／員工綁定類型切換。

**Acceptance Scenarios**：

1. **Given** 一般使用者已登入，**When** 呼叫公司主管管理 API，**Then** 回覆 403 與模組化訊息。
2. **Given** 一般使用者已登入，**When** 直接進入管理頁，**Then** 導向無權限頁並顯示指定訊息。
3. **Given** 系統管理員已登入，**When** 進入頁面，**Then** 可切換公司、主管與綁定公司三個標籤。
4. **Given** 管理員位於綁定公司標籤，**When** 切換主管或員工，**Then** 表單、查詢欄位與列表欄位同步顯示對應身分類型。

### Edge Cases

- 公司名稱去除前後空白後不得為空，且忽略大小寫不得重複。
- 同一使用者不得重複建立主管資料。
- 已綁定公司的主管不得被刪除；仍有主管的公司不得被刪除。
- 重複建立相同綁定或把同一主管綁到第二家公司都回覆衝突。
- 名稱查詢空白時回傳全部資料；沒有結果時顯示空狀態。
- 已停用的使用者不得新建為主管。
- 已停用、沒有 `EMPLOYEE` 角色、已建立主管資料或已綁定公司的使用者不得成為員工綁定候選。
- 取消綁定 API 必須核對成員類型，員工端點不得取消主管綁定，主管端點不得取消員工綁定。

## Functional Requirements

- **FR-001**：系統 MUST 允許系統管理員新增唯一名稱的公司。
- **FR-002**：系統 MUST 允許系統管理員查詢、修改及刪除公司。
- **FR-003**：公司名稱 MUST 去除前後空白、不得為空，且忽略大小寫唯一。
- **FR-004**：仍有成員綁定的公司 MUST NOT 被刪除。
- **FR-005**：主管 MUST 綁定既有且啟用的註冊使用者。
- **FR-006**：同一使用者 MUST NOT 建立多筆主管資料。
- **FR-007**：建立主管資料時系統 MUST 授予該使用者 `MANAGER` 角色。
- **FR-008**：系統 MUST 允許系統管理員查詢與修改主管職稱。
- **FR-009**：未綁定公司的主管 MUST 可被刪除，且移除其附加 `MANAGER` 角色。
- **FR-010**：系統 MUST 允許系統管理員建立及取消公司主管綁定。
- **FR-011**：一家公司 MUST 可綁定多名主管。
- **FR-012**：同一使用者（主管或員工）MUST 最多綁定一家公司。
- **FR-013**：系統 MUST 支援依公司名稱及主管姓名或帳號查詢綁定資料。
- **FR-014**：系統 MUST 以公司、主管、公司成員綁定三類資料表保存本功能資料。
- **FR-015**：所有管理 API MUST 僅允許 `SYSTEM_ADMIN`。
- **FR-016**：無管理 API 權限時 MUST 回覆「[公司主管管理] [api] 無系統管理員權限。」。
- **FR-017**：前端管理路由 MUST 僅允許 `SYSTEM_ADMIN`，且提供公司、主管、綁定三個標籤。
- **FR-018**：無管理頁權限時 MUST 顯示「[公司主管管理] [頁面] 無系統管理員權限。」。
- **FR-019**：公司名稱、公司說明與主管職稱 MUST 以 Unicode 格式保存，繁體中文寫入及讀回不得轉為問號。
- **FR-020**：前端原「綁定」標籤 MUST 改名為「綁定公司」。
- **FR-021**：系統 MUST 允許系統管理員將符合資格的已註冊員工綁定至公司及取消綁定。
- **FR-022**：員工綁定候選 MUST 為啟用、具有 `EMPLOYEE` 角色、尚未綁定公司且尚未建立主管資料的使用者。
- **FR-023**：系統 MUST 支援依公司名稱及員工姓名或帳號查詢員工綁定資料；空白條件 MUST 回傳全部員工綁定。
- **FR-024**：員工綁定與主管綁定 MUST 共用一人一公司的資料庫唯一限制，且取消操作 MUST 驗證成員類型。

## Key Entities

- **Company**：唯一公司名稱、可選說明與建立/更新時間。
- **SupervisorProfile**：既有使用者的一對一主管資料與職稱。
- **CompanyMembership**：使用者與公司的綁定；使用者唯一，公司可對應多筆成員。

## Assumptions

- 既有第 13–15 列已完成內容保留；本次程式增量只處理「任務指派」第 16–17 列「預計開發」的「公司主管管理」子模組，第 18 列以後未標示「預計開發」者不在範圍。
- 公司 CRUD 採實體刪除；為保護關聯，存在成員綁定時先拒絕刪除。
- 主管資料是既有使用者的附加身分，不建立獨立登入帳號。
- 員工綁定使用既有通用唯一綁定模型，不建立第二張員工專用關聯表。
- UI 以 `uiux/0.共用樣式` 與 `uiux/1.1.使用者分權` 的視覺與操作流程為準。

## Success Criteria

- **SC-001**：系統管理員可在 2 分鐘內完成公司新增、修改、查詢與刪除流程。
- **SC-002**：100% 主管建立案例都只能選用既有且啟用的註冊使用者。
- **SC-003**：一家公司綁定兩名主管成功率為 100%，同一主管綁定第二家公司拒絕率為 100%。
- **SC-004**：公司名稱與主管名稱查詢的預期資料命中率為 100%。
- **SC-005**：管理 API 與頁面的非管理員拒絕案例通過率為 100%。
- **SC-006**：後端整合測試、Postman、前端建置與 Cypress 規格全部通過，task 與 checklist 完成率為 100%。
- **SC-007**：公司名稱、公司說明與主管職稱的繁體中文資料經 SQL Server 寫入後，原字讀回正確率為 100%。
- **SC-008**：「綁定公司」標籤名稱、主管／員工切換、表單與列表欄位符合率為 100%。
- **SC-009**：員工綁定、雙條件查詢、第二家公司拒絕、取消後改綁的後端、Postman 與 Cypress 案例通過率為 100%。
